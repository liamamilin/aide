## 原因与证据

当前 PyQt5 的 `PyQtMonitor` 监视 C++ 创建的 QObject。工作线程销毁网络回复后，其 `destroyed(QObject*)` 通知会排队到监视器所在的主线程。监视器按原生地址查找当前包装对象；若新回复在通知送达前复用了旧地址，旧通知就会把新回复的包装对象标为失效，尽管管理器仍持有活着的原生回复。

这解释了此前两种失败：信号回调把失效包装误判成连接断开；或 `post()` 返回与信号连接之间包装失效，产生内部错误。它也解释了只保留 Python 引用、关联管理器或升级临时 SIP 绑定仍不能可靠消除问题。

- 临时诊断绑定捕获了主线程 `PyQtMonitor::on_destroyed` → `sipInstanceDestroyed` 的调用栈。[原生诊断](assets/qt-reply-lifecycle-native-diagnostic-2026-10-09.log)
- 使用原始已安装绑定，在主线程暂缓通知、工作线程复用旧地址后再投递通知，确实使新包装失效；修复前返回连接失败。[受控失败](assets/qt-reply-lifecycle-native-red-2026-10-09.log)
- 修复后对模型、搜索分别重复 3 轮；每轮都要求发生真实地址复用和监视器误标，然后验证成功返回及仅 1 次 HTTP 请求。[模型](assets/qt-reply-lifecycle-native-model-2026-10-09.log)、[搜索](assets/qt-reply-lifecycle-native-search-2026-10-09.log)

源码核对使用 [PyQt5 5.15.11 官方源码包](https://files.pythonhosted.org/packages/0e/07/c9ed0bd428df6f87183fca565a79fee19fa7c88c7f00a7f011ab4379e77a/PyQt5-5.15.11.tar.gz)中的 `qpy/QtCore/qpycore_event_handlers.cpp`。诊断扩展仅在临时子进程使用；项目与全局依赖未更改。

## 实现

- 新增 `ai_desktop/services/qt_reply.py`，供模型流和搜索使用。包装失效时，查询本次独立管理器实际持有的唯一直接回复子对象，重新绑定后继续读取原请求。
- 覆盖信号连接、响应头、流读取、结束检查和取消/超时后的释放。绑定调用之间也可能失效，因此每次操作最多尝试取得稳定包装 8 次；实际对象消失或无法取得稳定包装仍按连接失败结束。
- 不保存并解引用旧地址，不重新发送 HTTP，不重置流解码器，不关闭垃圾回收，不增加全局对象保留表。受控实验只比较有效包装的地址以验证复用，不用地址访问内存。
- 原生回复真正销毁时，模型和搜索均及时结束，唤醒等待循环；取消、时长上限、连接超时和响应超时保留原有结果与部分文字，只发送一次终态。
- 搜索增加明确的启动标记，迟到的启动前回调不终止未启动请求，重复启动也不会重复发送。原线程与定时器清理修复保留，`run_worker.py`、`search_executor.py` 和原模型销毁回归未修改。
