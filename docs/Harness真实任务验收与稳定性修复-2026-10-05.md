# Harness 真实任务验收与稳定性修复

更新日期：2026-10-05。接续 [H6 收尾](H6统一运行时收尾与桌面验收-2026-10-05.md)，本轮使用源码原生 macOS Qt 窗口和本机 `qwen3.5:9b-mlx` 验收现有工作流，修复实际发现的问题，不扩大模型或工具范围。

## 首次发送的思考配置竞态

打开对话窗会异步请求 `/api/tags` 和 `/api/show`。此前立即发送时，模型声明可能尚未到达；配置中的“关闭思考”被当作未知能力，实际请求退回 `think: null`。本机 9B 的首次验收因此在 512 token 输出预算内只生成思考，最终答案为空并标记 limited。这不是新会话历史污染，而是请求准备顺序错误。

现在，当当前选中模型的后台能力检查已经运行、声明未知且用户指定了思考控制时，发送和重新生成会等待这次检查完成。准备阶段保存解析好的配置、动作规则、材料和附件引用，不提前写入用户消息或启动推理。检查完成后使用对应模型声明恢复发送；最多等待 6 秒，超时或服务不可用时停止并保留草稿，不静默降级。停止、隐藏、新建会话及修改模型、Agent、设置、动作或 profile 都会取消准备；迟到结果不能重新启动任务。动作材料恢复时同时恢复快捷动作面板。

已有有效缓存和显式“模型默认”不增加等待。模型已经完成检查但不支持所选思考值时，仍沿用可见提示和模型默认的既有行为。此修复复用当前界面的能力检查；没有为任意不同的动作/profile 模型增加一套独立预检。工具任务仍走 H5 的逐次准入。

## Qt Worker 生命周期

首次原生真实模型长链路验收中出现 `EXC_BAD_ACCESS / SIGBUS`。macOS 报告栈包含 SIP 类型转换和 `QObject.sender`；结合代码，问题是线程的 `isFinished()` 已为真，但排队的 `finished` 回调尚未送达，控制器提前 `deleteLater()`，后续回调再通过 `sender()` 读取已释放的 Qt 对象。

现在显式绑定 Worker 引用传递完成、运行事件和命令确认，控制器不通过 `sender()` 查这些信号的来源。退休线程保留到 UI 线程观察到 `finished` 后才释放，继续核对请求/会话身份及取消状态。新增回归覆盖“线程已结束但通知未到达”和 20 次连续真实 Qt HTTP 请求，核对回答、线程释放及无 sender 访问。本轮后续真实模型链路未再次出现此崩溃；不据此承诺所有原生崩溃均已消除。
