# 上下文管理设计与问题分析

日期：2026-09-23

## 当前请求如何组成

普通消息发送给 Ollama 的内容由两部分组成：

1. 当前界面所选 Agent 的 `system_prompt`；
2. 当前会话内最近 `OLLAMA_MAX_ROUNDS` 轮用户与助手消息。

重新生成时，同一问题只带入用户当前选择的答案版本。快捷动作可以使用动作专属的系统提示，并根据“新对话 / 当前对话”模式决定是否保留当前消息历史。请求在提交时由 `StreamingChatWorker` 制作不可变快照；之后切换 Agent、模型或会话不会修改已经发出的请求。

Ollama 的 `keep_alive=30m` 只让模型权重留在内存，应用仍然在每次 `/api/chat` 请求中完整发送消息数组。它不是会话 ID，也不应保存上一段聊天历史。

## “新对话”的边界

点击“新对话”会：

- 取消并隔离正在生成的旧请求；
- 把当前会话 ID 设为 `0`；
- 清空内存消息和界面消息；
- 在下一次发送时创建新的数据库会话；
- 只使用新会话中的消息构造请求。

历史记录保留在 SQLite 中，但不会因为仍存在数据库里而自动进入新请求。

## 本次问题的证据与根因

用户复现时的旧会话 ID 36 保存了较长的 AI System 讨论，末尾还有一次被中断的“天天都需要你爱”。点击新对话后创建的会话 ID 37 只有一条新的用户消息和一条助手回复。因此，旧会话消息没有进入新请求。

会话 ID 37 的 `agent_id` 是 `code_expert`，应用日志也记录了“New conversation started (agent=代码专家)”。回复中的“这不是一个编程问题”“如果在程序开发中实现”以及代码方案，均来自代码专家的系统提示风格。截图此时显示的却是“通用助手”。实际问题是界面显示的 Agent 和控制器用于请求的 Agent 曾出现不同步，造成了类似上下文污染的结果。

日志进一步定位到了完整触发链：保存自定义 Agent 后，正在使用的自定义 Agent 被删除；`AgentManager` 回退到默认“代码专家”，但聊天窗口仍拿已删除的 ID 刷新下拉框。查找失败抛出 `StopIteration`，而异常发生在 `blockSignals(True)` 之后，导致下拉框信号未恢复。重建后的下拉框视觉上停在第一项“通用助手”，控制器却保持“代码专家”。

## 已实施修复

- 普通发送和点击“新对话”时，以界面当前可见的 Agent 作为最终权威状态；发现控制器与界面不同步时，先自动校正再创建请求。
- 删除当前自定义 Agent 时，刷新逻辑显式接收控制器已经选定的回退 Agent；无论刷新是否异常，都会在 `finally` 中恢复下拉框信号。
- 新会话数据库记录使用本次实际请求的 Agent，不再使用可能滞后的控制器字段。
- 每次请求写入不含正文的边界日志：会话 ID、Agent ID、上下文消息数量和角色序列，便于以后判断是历史污染、Agent 错配还是模型自身回答偏差。
- 新增回归测试：先完成旧会话，人工制造界面/控制器 Agent 不一致，再新建会话；断言发给假 Ollama 的内容严格等于“通用助手系统提示 + 新用户消息”，不包含任何旧消息。

## 仍需继续设计的边界

当前数据库只在会话级记录一个 `agent_id`。如果用户在已有多轮对话中直接切换 Agent，后续请求会保留原消息历史、改用新的系统提示，而历史列表仍只能显示会话创建时的 Agent。这个行为不是本次新对话问题的根因，但也可能让用户误以为有隐藏上下文。

下一步建议把 Agent 切换做成显式选择：

- “以新 Agent 开始新对话”（推荐默认）；
- “在当前上下文继续”（明确保留历史）。

同时在界面中显示当前请求的上下文范围，例如“新对话 · 0 条历史”或“当前对话 · 最近 6 轮”，让上下文边界可见、可核验。
